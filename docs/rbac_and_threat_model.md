# RBAC Matrix and Threat Model

## Role-Permission Matrix

The policy I went with is the `ROLE_PERMISSIONS` dict in `server/rbac.py`. Every server endpoint declares its rule with a decorator, and an endpoint without one is refused bc it's deny by default. `tests/test_rbac.py` has this matrix typed out by hand / checks every role against every permission. A denied request gets 403 and an `access_denied` audit entry.

"Anon" = request with no login.

## Threat Model

The assets I identified: message contents, sender anonymity, metadata (who receives how much, and when), audit log integrity, fair quotas, availability.

The adversaries I identified: a curious or malicious server operator or Admin, a malicious Sender, malicious Recipient, a curious Moderator, an outsider who steals the database, a network observer.

My High Value Targets (HVTs) are the epoch signing key (can create tokens), the audit signing key (can re-sign a rewritten log), the Admin account (controls roles and keys), users' private keys.

I progressively added to this as I went along the implementation and discovered new threats to be aware of.  


| #   | Threat                                                                                  | Impact                                                 | Defense                                                                                                                                                                                                                                                                                                                                                                                                                                            | Residual risk                                                                                                                                                                                                                                                                                    |
| --- | --------------------------------------------------------------------------------------- | ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| T1  | Compromised Admin or server tries to read messages                                      | Confidentiality                                        | End-to-end encryption; private keys exist only on clients machine; I don't have any endpoint return content to Admin users                                                                                                                                                                                                                                                                                                                         | Future messages are at risk only combined with T3. Creates target on the back of the endpoints - client holds the keys locally                                                                                                                                                                   |
| T2  | Compromised Admin or server tries to identify senders                                   | Anonymity                                              | Blind signatures so issuing token can't be matched to using it (mechanism described in report); no sender id on messages or sender-side log entries; the issuance table is deleted when each epoch ends; sender-side log times rounded to the hour                                                                                                                                                                                                 | Timing and traffic analysis (T9) - someone watching the server's traffic could see the order of events and IP addresses (my logs don't store IPs) - i.e. Alice logs in and gets token, then message sent shortly after and thus likely came from her. Assumes low activity on the app.           |
| T3  | Public key substitution: an Admin approves an attacker's key in place of Bob's          | Future confidentiality                                 | Clients pin each recipient's fingerprint on first use and do not send if it changes; key approvals are signed audit events with the fingerprint; users can also compare fingerprints IRL                                                                                                                                                                                                                                                           | If the key got swapped before the first contact, the client would be trusting the malicious key - trust on first use. Only rly caught by in-person fingerprint check                                                                                                                             |
| T4  | Compromised Admin creates fake Senders, or the signing key leaks and tokens are minted  | Spam, quota bypass                                     | Registrations and role grants are signed audit events; an alert fires if more distinct tokens are used in an epoch than the server issued                                                                                                                                                                                                                                                                                                          | Minted tokens look like real tokens. Given single issuer, it can be detected but not necessarily prevented.                                                                                                                                                                                      |
| T5  | A Sender shares their token                                                             | Accountability                                         | A token is still only good for one message per round; a freeze applies to whoever holds it; Stolen or sniffed token isn't enough on its own because you need the token's private key too to send a valid envelope                                                                                                                                                                                                                                  | Inherent to bearer tokens                                                                                                                                                                                                                                                                        |
| T6  | Token forgery, reuse, or replay                                                         | Quota bypass                                           | Tokens are RSA blind signatures over full-domain hash of the epoch plus the token public key, so you can't fake one or combine old signatures into a new one; new signing key every epoch so old tokens just stop working; `spent_tokens` primary key means one message per token per round, even if a bunch of requests hit at the same time; the token key also signs the round and recipient so a captured send can't be pointed somewhere else | Nothing rly practical without the signing key (T4)                                                                                                                                                                                                                                               |
| T7  | Flooding or denial of service                                                           | Availability                                           | One token and one message per round caps what any one sender can push; requests over 64 KB get cut off; 5 failed logins locks the account for 5 min; alert after 5 invalid tokens in a round                                                                                                                                                                                                                                                       | Worst case is bounded by how many senders there are. Network-level DoS (just flooding the machine with traffic) is out of scope for this project.                                                                                                                                                |
| T8  | Repudiation                                                                             | Accountability                                         | Every message is signed by a token key the server blind-signed, so it provably came from a real token holder and wasn't changed; Admin and Mod actions are logged with their user id and signed so they can't deny them later; flags get checked against the sender's commitment so nobody can argue about what the message actually said                                                                                                          | On purpose, accountability is tied to the anonymous token and not a person - a sender can deny it was them, which is just the anonymity working. Log signatures are only as trustworthy as the audit key (T12).                                                                                  |
| T9  | Metadata and traffic analysis                                                           | Anonymity                                              | Tokens get picked up at login, separate from sending; the send goes over a fresh connection with no login or cookies; I don't store IPs or exact send times                                                                                                                                                                                                                                                                                        | Someone watching live traffic can still line up "Alice logged in" with "a message showed up right after", esp. with only a few users. Fixing this rly needs Tor or a mix network.                                                                                                                |
| T10 | Fraudulent flagging                                                                     | Unfair moderation                                      | Recipient has to hand over the real AES key - it has to match the commitment the sender signed AND decrypt the ciphertext, so they can't make up nasty text and pin it on a token; alerts never freeze anything on their own, a mod always decides                                                                                                                                                                                                 | A bunch of people flagging harmless stuff is more of a policy problem than a crypto one                                                                                                                                                                                                          |
| T11 | Curious Moderator                                                                       | Privacy                                                | Mods only see what a recipient chose to reveal, and never who sent or received it; mods can't also be admins; every mod action is logged with their id                                                                                                                                                                                                                                                                                             | Flagged content is shown to mods on purpose - that's the whole point of flagging                                                                                                                                                                                                                 |
| T12 | Audit log tampering                                                                     | Accountability                                         | DB triggers block edits and deletes; hash chain so changing an old entry breaks everything after it; Ed25519 signature on every entry so the chain can't be recomputed without the audit key; mods' clients save the latest head hash and check it's still there next time                                                                                                                                                                         | Someone with both the DB and the audit key could rewrite everything after the last head hash a mod saved                                                                                                                                                                                         |
| T13 | Database theft                                                                          | Confidentiality                                        | Only ciphertext is stored; passwords are scrypt hashes (slow + salted); session ids only stored as hashes so stolen ones don't work                                                                                                                                                                                                                                                                                                                | Metadata still leaks, i.e. how many messages each recipient got per round. Also the current epoch's signing key sits in the DB, so a theft mid-epoch could mint tokens until the next round (T4).                                                                                                |
| T14 | Privilege escalation, insecure direct object references                                 | All                                                    | Deny by default; one policy table that everything goes through; ownership checks so you can only touch your own messages; separation of duties; a test for every cell in the matrix                                                                                                                                                                                                                                                                | Bugs in my own code that I haven't caught                                                                                                                                                                                                                                                        |
| T15 | Script injection through message text (XSS in the web UI, escape codes in the terminal) | Key theft, actions as the victim                       | Jinja autoescapes everything and I never use its safe filter (a test checks for this); the CSP allows no scripts at all; the server is a JSON API with no HTML pages; the CLI strips control characters before printing                                                                                                                                                                                                                            | A future template mistake, though the CSP is still there as a backstop                                                                                                                                                                                                                           |
| T16 | Other websites attacking the local UI (CSRF, DNS rebinding)                             | A malicious page makes the user send, flag, or approve | Only listens on 127.0.0.1; CSRF token on every form, even login; `SameSite=Strict` cookie; Host header has to be `127.0.0.1` or `localhost` on the right port, which stops DNS rebinding; anything that changes state is POST only                                                                                                                                                                                                                 | If the local machine itself is compromised all bets are off - out of scope                                                                                                                                                                                                                       |
| T17 | Stolen client key file                                                                  | Confidentiality for that user                          | Private key file is encrypted with the user's password and only readable by the owner; it never leaves the client                                                                                                                                                                                                                                                                                                                                  | Same password is used to log in, so a malicious server that also got hold of the key file could unlock it. Separate passwords would fix this but it's more annoying to use.                                                                                                                      |
| T18 | Abusive sender keeps going in later rounds                                              | Abuse prevention                                       | Mod freezes the flagged message's token and the message gets withdrawn; if the token was already spent it just stays unusable and the freeze is still logged as the mod's decision; frozen tokens get rejected at send and raise an alert                                                                                                                                                                                                          | A fresh token next round can't be linked back to the frozen one, so the same person can just send again. That's the cost of unlinkable tokens - on purpose there's no token-to-user mapping. A longer token lifetime (policy) would make a freeze cover more rounds but makes messages linkable. |
